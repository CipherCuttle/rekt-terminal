# REKT INK(CUBATOR) — North Star MVP v0

**Status:** CANONICAL / LOCKED MVP PRODUCT THESIS

**Locked:** 2026-09-06

## One sentence

REKT INK(CUBATOR) is a persistent multiplayer builder world where people turn weird ideas into working artifacts, with a personal Mission command center, truthful progress/evidence, meaningful collaboration, visible history and a developer surface that plugs real work into the world.

## What it is not

INK(CUBATOR) is not:

- a formal incubator application funnel;
- a generic hackathon submission site;
- a Linear/Jira replacement;
- a Discord replacement;
- a Twitter/LinkedIn clone for builders;
- an XP farm;
- a wallet-first Web3 dashboard;
- a generic AI wrapper;
- a requirement that every project use REKT/Chibi assets;
- an official promise of Ink/Kraken funding, transition, support or affiliation.

REKT/Chibi are the origin culture, identity, distribution and aesthetic DNA. They are not required subject matter for every build.

`REKT-BORN ≠ REKT-ASSET-REQUIRED`.

## The desired feeling

A visitor should feel that they discovered a live underground build world.

A Player should feel that the product knows:

1. who they are;
2. what they are trying to ship;
3. where the project is relative to the ship condition;
4. what changed;
5. what is blocking progress;
6. what the most useful next move is;
7. who can help;
8. what they have already built and helped create.

The platform should be visually expressive but operationally calm enough to remain open for hours.

## The founding-cohort MVP

The first 8–10 invited Players must be able to use the complete loop, even if some operational work remains manually curated behind the scenes.

### 1. Become

A Player creates a persistent profile/character with minimal friction. GitHub is the default technical identity path for builders, but character metadata must never become a hard requirement for core identity.

### 2. Declare

The Player joins a Round or creates/selects a Mission and answers the smallest possible question:

> **What are you shipping?**

A Mission has a clear goal, ship condition, deadline/window where applicable, current focus and one dominant next move.

### 3. Connect

The Player may connect a GitHub repository. The system derives useful context rather than making the Player manually enter stack, contributors, recent activity and obvious project facts.

Private source data remains private unless explicitly projected publicly.

### 4. Build

The personal Command Center becomes the default logged-in surface. It shows the Mission, ship condition, Thread/progress, blockers, next move, stack, Party/collaborators, Help Beacon state, recent Signals/activity and expandable evidence.

INK(CUBATOR) tracks movement toward shipping, not every task.

### 5. Prove

The system distinguishes:

`CLAIM → OBSERVATION → PROOF`

Participant-controlled inputs may create claims. Trusted adapters/human actions/rules may create observations. Only Inkubator authority may promote sufficient evidence to PROVEN.

### 6. Help

Players can discover other builders/projects, follow/watch them, comment in project context, emit Help Beacons, offer Assists and mark useful help as accepted.

Raw engagement is not reputation.

### 7. Earn

Cheevos celebrate meaningful state transitions: first working build, recovery, first external tester, accepted Assists, Party formation, Ships and other real milestones.

No reward for login streaks, raw comment volume, follower farming or screen time.

### 8. Ship

A Project can be submitted through a bounded Ship flow. Evidence is reviewed/verified according to the current trust model and produces a durable Ship Receipt when accepted.

The artifact, builders, Party and Assists are preserved in the Ship history.

### 9. Remember

The Player survives the Round. The Project survives the Round. Ship history, accepted Assists, Cheevos, traits and other reputation-bearing facts persist.

Profiles tell the story of a builder's ecosystem history rather than acting as generic social profiles.

### 10. Repeat

The Player can enter the next Mission/Round without starting over. Previous history creates identity and social context, but should never create pay-to-win or permanent exclusion from future participation.

## Public/product spaces

The product has four major surfaces.

### WORLD

Public discovery and broadcast surface. Shows active Round, builders, Ships, Signals, Help Beacons, highlights and archive. Highest atmosphere.

### COMMAND

Personal Mission cockpit. Shows what matters now. One dominant `NEXT MOVE`. Highest operational focus.

### PROJECT

Shared Project room. Shows goal, state, Party, needs, updates, evidence, comments, Assists and Ship readiness.

### PLAYER

Persistent builder identity and career/history surface: current Mission, Ships, Assists, traits, Round history and meaningful reputation.

A fifth operational surface, `OPS`, exists for trusted operators and moderation; it is not part of the public game-world presentation.

## The developer-platform launch pillar

The launch MVP includes a deliberately small developer surface:

- public protocol/contracts;
- TypeScript SDK;
- CLI;
- MCP bridge;
- small React/embed surface where useful.

The desired launch effect is that a builder can connect a real Project, inspect Mission status from the terminal or coding agent, post bounded updates/claims/Help Beacons, and see the world react to real external evidence.

The developer platform must never let participant-controlled code mint PROVEN truth, grant Cheevos, approve Ships or alter reputation directly.

## Social/reputation thesis

The product is multiplayer because work is visible and help has consequences, not because it contains a generic feed.

First-class social primitives:

- Follow Player;
- Watch Project;
- Comment/reply/reaction in project context;
- Help Beacon;
- Assist;
- Party/project membership;
- external testing;
- Proven Pull (later in MVP only if the underlying invite→Ship data exists truthfully).

Reputation is multidimensional and derived from durable behavior such as Ships, accepted Assists, collaboration and recoveries. There is no single universal engagement XP score in MVP.

## Visual North Star

The visual system has one cross-product grammar and three intensity modes:

- **BROADCAST** — atmospheric World/Round/culture surfaces;
- **COCKPIT** — calm, dense, truthful operational surfaces;
- **ARTIFACT** — quiet presentation where the thing built dominates.

The shared "röd tråd" is **THE THREAD**: a continuous Signal/progress/history grammar reused for Round lifecycle, Mission progress, Player history, evidence chain, Ship history, graveyard/resurrection and future build replay.

Acid green is scarce and semantic: proven/current/actionable state, never generic decoration.

## Product doctrine

1. **SHIP > TALK.** Working artifact beats deck.
2. **ONE STRONG CONSTRAINT.** Permanent machine broad; each Round narrow.
3. **NEXT MOVE IS SACRED.** Reduce cognitive load to the most useful current action.
4. **TRUTH BEFORE GAMIFICATION.** Game language overlays real state; it does not manufacture it.
5. **HELP MUST MATTER.** Assists and testing make networking productive.
6. **FAILURE REMAINS LEGIBLE.** Dead/stalled Projects may produce postmortems, graveyard history and later resurrection rather than disappearing.
7. **ARTIFACT FIRST AT SHIP.** Ceremony yields to the thing that was built.
8. **NO FAKE LIVE ACTIVITY.** Fixtures/development data must remain unmistakably non-real.
9. **LOW FRICTION, HIGH MEANING.** Ask fewer questions; derive context; make each action consequential.
10. **THE EXPERIENCE CAN FEEL CHAOTIC; THE PROTOCOL CANNOT BE.**

## MVP success test

For the founding cohort, the product thesis is supported if most invited users can enter without operator hand-holding, create a Mission, generate real progress/evidence, understand their next move, inspect/help another builder, and a meaningful subset actually Ships and wants another Round.

Initial learning targets, not contractual KPIs:

- 8–10 invited founding Players;
- at least 8 create a Mission;
- at least 6 generate meaningful project activity;
- at least 5 Ship;
- at least 4 interact meaningfully with another Project;
- at least 2 accepted Assists;
- at least 3 voluntarily want another Round.

If users do not understand progress, do not care about other builders, do not use help mechanics or do not return after shipping, those mechanics must be redesigned rather than protected by sunk cost.

## Launch-level wow moments

The MVP should aim for a small number of memorable, truthful moments:

- `rekt init` links a Mission/Project;
- `rekt status` shows the same canonical Mission state as the web app;
- a coding agent can read Mission/next-move context through MCP;
- a GitHub event changes observed state without manual duplication;
- a Help Beacon becomes visible to another builder;
- an external tester/Assist changes the Project's social/evidence history;
- a Ship produces a durable Receipt and shareable Artifact state;
- the shipped Project can display an Inkubator Ship/status mark that links back to its history.

## Reopen conditions

This North Star may be reopened only if founding-cohort evidence shows that the complete loop is materially wrong, not merely because one implementation phase is difficult or a library makes another architecture convenient.
